(1) Can the mocks or STRIPE_API_BASE turn on in a real Vercel production or preview deploy? No.
- Gate: lib/e2e-mock.ts e2eMockOn() returns false whenever VERCEL or VERCEL_ENV is set.
  Otherwise it needs E2E_MOCK=1, and in production it also needs E2E_PROD_BUILD=1.
- Vercel docs (vercel.com/docs/environment-variables/system-environment-variables) say VERCEL=1 and VERCEL_ENV are
  "Available at both build and runtime". So both the build-time gate and the runtime gates are closed on Vercel.
- Build time: I built with E2E_MOCK=1, E2E_PROD_BUILD=1 and VERCEL=1.
  - routes-manifest.json has no /v1 -> /e2e-mock rewrite; the only rewrites are BotID's (routes-vercel-flags.txt).
  - next.config decides the rewrite once at build, so a Vercel build never ships it.
- Runtime, on that build (runtime-gates.log):
  - flags + VERCEL=1 + VERCEL_ENV: /e2e-mock 404, /v1 404
  - no flags: 404 / 404
  - E2E_MOCK=1 only: 404 / 404
  - both flags, off Vercel: /e2e-mock 200 (intended for the e2e run); /v1 still 404 because the rewrite was not built in
- Edge middleware: the compiled .next/server/middleware.js keeps `function(a=process.env){return"1"===a.E2E_MOCK&&!a.VERCEL&&!a.VERCEL_ENV&&(...)}`.
  - Reading the whole object means nothing is inlined at build. The value is read from the edge runtime's process.env.
  - If the edge env lacked a variable, the gate would fail closed (E2E_MOCK would not be "1").
  - Its only effect is to let /v1/* past the account wall, and on Vercel that path has no rewrite, so it 404s.
- NEXT_PUBLIC_: e2eMockOn reads no NEXT_PUBLIC_ variable and is imported only by server code (route, middleware, next.config,

- STRIPE_API_BASE (lib/billing/stripe.ts): honoured only when NODE_ENV != production or e2eMockOn(). Vercel prod and preview are
